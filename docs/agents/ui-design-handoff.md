# UI / Design Handoff

## Current phase

Further 的首版 MVP 功能实现已经完成，基础真机运行暂未发现明显问题。当前 SwiftUI 页面以验证状态流、系统能力和业务闭环为主，是可替换的工程界面，不代表最终美学方案。

上一轮定制化视觉规范在真机上未成立，已被废止。下一阶段按 Apple 原生优先原则重新设计
业务界面，再独立讨论作品美术。当前工程界面仍只作为状态流参考，不作为最终布局依据。

## Start here

开始 UI 或美术讨论时，按顺序阅读：

1. `CONTEXT.md`：使用 Further 的规范领域语言。
2. `docs/product/product-philosophy.md`：理解产品为何存在，以及它刻意不做什么。
3. `docs/product/first-version-scope.md`：固定首版能力边界。
4. `docs/product/information-architecture.md`：理解单一作品主空间和各次级空间。
5. `docs/product/page-and-state-specification.md`：覆盖完整页面、状态与异常分支。
6. `docs/product/interface-principles.md`：遵守已确认的信息层级、交互和可访问性原则。
7. `docs/product/visual-foundation.md`：从已确定的视觉职责继续，而不是重新定义产品。
8. `docs/product/interface-aesthetic-direction.md`：理解真机评审后的设计重置。
9. `docs/product/interface-visual-system.md`：遵守首版原生组件与视觉范围。
10. `docs/research/apple-native-design-references.md`：按 Apple 官方依据校准设计判断。
11. `docs/technical/architecture.md`：当设计需要评估实现代价或系统限制时再阅读。

进入具体页面前，可以运行当前 App 或查看截图理解已有流程，但应把它视为功能原型，而不是视觉参考答案。

## Fixed constraints

- 当前作品是唯一主空间，不使用底部标签栏或数据仪表盘式首页。
- 作品从真实空白开始，只由真实记录点逐步形成。
- 每个页面只有一个明确的主要行动；关键入口可见、可理解，不依赖隐藏手势。
- 感受色与短记高于距离、时间和路线等客观事实；更远、更快不能被编码成更好。
- 收束后必须让用户感知本次记录进入作品，不能直接跳回静态更新后的首页。
- 沉默是合法表达，不是缺失、失败或待办。
- 不加入训练计划、统计比较、打卡奖励、分享社交、编辑删除或其他首版外能力。
- 第一正式版本只设计浅色外观和系统标准字号；深色模式及辅助功能大字号的视觉适配延期。
- 首版仍覆盖 VoiceOver、减弱动态效果、非纯颜色状态提示、可靠对比和运动中的单手操作。
- 业务界面优先使用 Apple 官方组件和系统默认行为；自定义视觉只用于作品画布、感受色和
  记录进入作品。

## Design priorities

按以下顺序收敛设计，避免先从设置页或孤立控件建立风格：

1. 当前作品空间：画布边界、真实空白、印记积累、开始入口及边缘导航。
2. 结束与收束：感受色、短记、沉默、室内距离和记录进入作品。
3. 跑步追踪：运动中可读性、暂停与结束确认、户外和室内降级状态。
4. 回望与单次记录：记忆优先、事实低声量、路线存在与缺失。
5. 作品完成与作品集：完成停留、开启下一幅、装裱和阶段回望。
6. 设置：保持朴素，服务权限与单位，不承担品牌展示。

## Questions to resolve

- 作品采用怎样的视觉隐喻、画布、材质与构图规则？
- 单条印记如何保留原始记录色，又随时间产生可追溯的演化？
- 感受色的数量、色值、选择方式和无文字标签体验如何成立？
- 沉默使用怎样的专属记录色和质感，既真实参与作品又不被误解为负面？
- 距离、配速等客观事实是否以及如何影响形式，而不变成隐藏的数据图表？
- 少量和大量记录如何都形成完整作品？浅色外观中如何保持稳定的作品身份？
- 新印记进入、作品完成和空间切换使用怎样的动效、触感与减弱动态替代？
- 当前作品、回望、作品集与设置的导航控件如何可发现而不喧宾夺主？

## Expected outputs

设计讨论结束时，至少应形成：

1. 一套明确的视觉方向及其选择理由，包含被放弃方案和关键权衡。
2. 原生组件选择、信息层级、颜色职责、文案、动效、触感和例外边界。
3. 六类核心空间的布局与全部关键状态，而不只是理想路径的静态首页。
4. 作品生成、记录进入和作品完成的规则说明，能够由工程实现并稳定复现。
5. 浅色标准字号基线、VoiceOver、减弱动态和运动场景的处理方案，并明确延期项。
6. 对现有产品文档的必要更新，以及一份分阶段、可单独验收的 UI 实施计划。

## Collaboration

设计阶段先讨论体验目标和方案权衡，再进入视觉细节。可以通过文字、线框、情绪板、静态稿或小型原型探索；任何探索产物都应明确是方向验证还是最终规格。

在设计方向和验收标准确认前，不修改生产 SwiftUI 代码。需要验证技术可行性时使用可丢弃原型，不让原型结构反向绑架正式架构。

发布前专项真机验收与 UI 设计并行但相互独立。真机发现的功能缺陷单独记录和修复，不把它包装成视觉改造。
